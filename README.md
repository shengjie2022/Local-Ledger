# 本地账本 · 微信 / 支付宝流水

修复版说明、验证结果及迁移注意事项见 [修复说明](docs/index.html)。

把微信、支付宝的**账单明细**文件拖进来，自动生成按**日 / 月 / 年**分组的流水账本；
再填一次「我现在实际还有多少钱」，就能**反推出每一笔支出之前账户里还剩多少**。

全程在你自己电脑上跑，**不联网、不上传、没有任何服务器**，账单数据只存在本机浏览器里。

---

## 〇、怎么启动（不需要部署服务器）

这是一个**纯静态本地应用**，没有任何后端、不用装环境、不用注册账号。三种启动方式，任选：

### 方式 A：双击 `启动账本.bat`（推荐）

自动起一个只读本地服务 → 等端口就绪 → 打开浏览器。
用完把那个黑窗口关掉（或 Ctrl+C）即可停止。

### 方式 B：直接双击 `index.html`

也能正常用（浏览器会读本地文件）。差别只在于：个别浏览器对 `file://` 下的本地存储限制更严，
此时建议改用方式 A。

### 方式 C：命令行（可带参数）

```powershell
python 启动账本.py                 # 仅本机，http://127.0.0.1:8899/
python 启动账本.py --lan           # 同时允许同一 WiFi 下的手机访问
python 启动账本.py --port 9000     # 换端口
python 启动账本.py --no-browser    # 不自动开浏览器
```

`--lan` 会在窗口里打印一个 `http://192.168.x.x:8899/index.html` 的地址，
手机连同一个 WiFi 直接输这个地址就能用（手机和电脑的数据各存各的，互不相通）。

### 搬到别的电脑 / U 盘

把**整个文件夹**拷过去就行，没有依赖、没有安装步骤。
对方机器有 Python 就用方式 A，没有就直接双击 `index.html`。

### 想放到静态托管上（可选）

整个应用就是 `index.html` + `styles.css` + `js/`，扔到任何静态托管（GitHub Pages、对象存储等）都能跑。
但注意两点：

- **账单文件仍然在浏览器本地解析**，不会上传到服务器——托管方拿不到你的账单
- 但托管页面本身是公开的（HTML/JS 谁都能看），而且**数据存在各自浏览器的 IndexedDB 里**，
  所以每台设备的数据互相独立，跨设备要用「导出备份 JSON → 恢复备份」

### 关于"服务"到底是什么

`启动账本.py` 起的那个 HTTP 服务只干一件事：把 `index.html`、`styles.css`、`js/*.js` 这几个静态文件
发给浏览器。**账单 CSV 从头到尾都在浏览器里用 FileReader 读取和解析，一个字节都不会经过这个服务。**

### 1. 导出账单明细（两个平台各导一份）

**微信**
> 微信 → 我 → 服务 → 钱包 → 账单 → 右上角「…」→ 账单明细 → 常见问题 → 下载账单
> → 选「用于个人对账」→ 选时间范围 → 接收账单（邮件收到压缩包，解压后是 CSV）

**支付宝**
> 支付宝 → 我的 → 总览 → 右上角「账单」→ 右上角「…」→ 开具交易流水证明
> → 选时间段 → 导出账单（CSV）

> ⚠️ 一定要导「**账单明细**」，不是「账单概览」/「月账单」。导错了会提示找不到表头。

### 2. 拖进账本

打开 `index.html`（或双击 `启动账本.bat`），把 CSV 文件拖到左边虚线框里。
微信和支付宝的文件可以一次全拖进去，会自动识别来源。

支持：CSV / TXT / TSV，GBK、GB18030、UTF-8、UTF-8 BOM 编码都能读。

### 3. 填基准余额

左侧「② 余额反推」里，会列出所有账户（`微信·零钱`、`微信·招商银行(1234)`、`支付宝`…），
逐个填上**你现在实际有的钱**，账本立刻把每一笔交易前后的余额倒推出来。

> 基准日默认取账单最后一笔交易的日期。如果账单没更新到今天，把基准日改成「账单覆盖的最后一天」，
> 否则那段时间没被记录的收支会让反推余额偏大（界面会黄条提醒）。
>
> **基准日一旦你手动改过，账本就不会再自动覆盖它**（导入新文件也不会）。
> 想恢复自动，点基准日右边的「↺ 最后一笔」。
> 如果基准日早于账单最后一笔交易，界面会提醒你 —— 因为基准余额会被当成最后一笔之后的余额来倒推。

## 二、余额是怎么反推的

你只需要知道**现在还剩多少钱**（基准余额），剩下的账本自己倒着算：

```
某笔交易「前」的余额 = 该笔「后」的余额 − 该笔的资金变动
```

- 收入：往前推，余额变少
- 支出：往前推，余额变多
- 从最后一笔一路倒推到第一笔

### 两种口径

| 口径 | 含义 | 适合 |
|---|---|---|
| **按账户分别**（默认） | 每个账户各自填余额、各自倒推 | 「这笔外卖付之前，我零钱里还有多少」 |
| **全部合计** | 所有账户合并成一个总资产倒推 | 「这笔买完，我全部家当还剩多少」 |

明细表里同时给出三列：**账户余额(前)**、**账户余额(后)**、**合计余额(后)**，切换口径即可。

## 三、它会替你处理的脏活

| 情况 | 处理方式 |
|---|---|
| 「交易关闭 / 支付失败」 | 自动排除（钱并未实际付出） |
| 「已全额退款」 | 净额记 0；支付宝有「成功退款」列的按实际退款额扣减 |
| 支付宝「交易成功但对方已退款」 | 视为全额退回，净额记 0（不再按原金额计支出） |
| 支付宝「服务费」 | 计入支出（手续费是实打实多扣的钱） |
| 部分退款但查不到金额 | 按原金额计，界面黄条提醒，可手动排除该笔 |
| 「不计收支」（零钱充值、零钱提现、余额宝转入转出…） | 识别为内部划转，落到具体账户和方向上；规则可在左侧「⑥ 规则」里改 |
| 跨平台同一笔转账记了两遍 | 按「同额 + 时间在 10 分钟内 + 一收一支」判定并提示，确认后可一键排除 |
| 同一个文件导了两遍 | 用**内容指纹**（不只是文件名）识别，导入时弹出提示，默认跳过 |
| CSV 里某行有未转义的逗号 | 自动定位错位并重建该行的列映射，一笔都不丢 |
| 余额算出来是负数 | 提示「可能漏了收入流水或基准余额填大了」 |
| CSV 里带引号的逗号/换行字段 | 正确按引号规则切分 |

分类（餐饮 / 交通 / 购物 / 日用 / 居住 / 通讯 / 生活 / 医疗 / 教育 / 娱乐 / 人情 / 宠物 / 数码 / 服饰 / 保险）
按关键词自动归类，顺序即优先级，可在「⑥ 规则」里改关键词、改优先级、临时停用某条，
也可以**自己新增 / 删除规则**。

> 手动记一笔时你填的分类会原样保留，不会被关键词表改掉
> （比如填「投资」就还是「投资」，不会被改成「其他」）。

## 三·五、账本体检

导完账单先看一眼「账本体检」面板，它会替你把几类"看起来没问题、其实账已经错了"的问题喊出来：

| 检查项 | 查什么 |
|---|---|
| 导入质量 | 每个文件读到多少行、解析出多少笔、跳过了多少行、为什么跳过、文件编码、文件指纹 |
| 账单月份连续性 | 中间是不是缺了某个月的账单（缺了余额反推就全错） |
| 重复记账检查 | 同一个文件导了两次；跨平台疑似同一笔 |
| 余额链自洽性 | 有没有负余额；合计口径和分账户口径对不对得上；哪些账户还没填基准余额 |
| 「不计收支」识别 | 有没有划转流水没匹配到规则，导致余额链条断了一环 |
| 退款处理 | 部分退款金额查不到、部分退款仍按全额计的笔数 |

顶上的分数是体检分（0~100）：出现「异常」扣得多，出现「提醒」扣一点。

## 三·七、每个文件的退款方式

支付宝账单里退款有两种形态：**单独一行退款收入**，或者**在原支出行上标「已退款」**。
账本会自动判断，但每个文件可以在文件列表里单独指定：

- **自动** —— 用文件探测的结果（默认）
- **按原样** —— 认定退款是独立一行，原支出按全额计
- **按状态净额** —— 认定退款标在原行上，按状态扣减

### 跑自检

```powershell
python test\make_fixtures.py
node test\smoke-test.js
```

覆盖 225 项断言：GBK 解码、微信/支付宝新旧两种表头、退款的多种形态、内部划转双向对冲、
按账户与合计两种口径的余额反推、日/月/年分组汇总、重复检测、导出的列结构与数值精度，
以及「反推结果必须与正向流水逐笔一致」这条硬校验。

本轮新增的断言集中在这些容易算错的地方：

- 支付宝「对方已全额退款」净额必须是 0（不是 88）
- 支付宝服务费必须计入支出（100 + 2.5 = 102.5）
- 手动记一笔的分类不能被关键词表改掉
- 余额按分取整，不能留下 `34999.999999999985` 这种浮点尾巴
- 跨平台重复检测要能查出相隔 2 分钟的同额交易，且不误报相隔 20 分钟的
- 列错位的行不能整行丢掉，且修好后金额/收/支/对方/商品都要读对
- 有基准余额但没流水的账户，合计基准余额不能少算
- 图表 SVG 的弧长之和必须等于周长（防止画歪还不报错）
- 体检必须能查出缺失月份、重复文件、未匹配的划转、部分退款金额未知

### 二次复查又抓出并修掉的问题

写完功能后专门又过了一遍代码，靠**实际复现**（不是读代码猜）又找出 6 个问题，
都已修掉并补了回归断言：

| 问题 | 后果 |
|---|---|
| 去重弹窗按 Esc / 点遮罩关闭时，导入的 promise 没人结 | **导入永久卡死**，界面看着像什么都没发生 |
| 切分点不允许重复 | 一个字段被逗号劈成 3 段以上时，整列错位，商家名被读成乱码 |
| `'内部划转：' + rule.note \|\| acc` 的运算符优先级 | 规则没有 note 时标记显示「内部划转：undefined」 |
| `for...in` 遍历基准余额对象 | 会把原型链上的属性也算进合计余额 |
| `isFinite(null)` 返回 true | 金额为 null 的行没被拦住，重复检测直接抛异常、导出也崩 |
| 警告区用 `innerHTML` 拼账单内容 | 商家名里带标签就会往页面里插标签（已全部转义） |

另外还修了：`IndexedDB` 存不下时降级到 localStorage，下次启动却被 IndexedDB 里的旧数据盖掉
（会静默丢数据）；汇总金额的浮点尾巴；手动记录用 `Date.now()` 当 id 可能撞车。

第三轮又补了两处：

- **启动器端口冲突**：以前只要端口被占用就当成"自己的服务还在跑"并把浏览器打开过去。
  现在会先探测端口上到底是不是本地账本 —— 是就直接复用，不是就明确提示"被别的程序占了"并建议 `--port` 换端口。
- **图表边界**：空数据 / 单类别 / 负值 / 超大金额 / 标签里带 HTML 的输入都补了断言，
  保证 SVG 里不会混进 `NaN`、`undefined` 或未转义的标签。

### 第四轮复查（专门查"会不会把账算错"）

前三轮修的是功能缺陷，这一轮换了个角度：用随机数据 + 极端输入去撞**余额链条的不变量**
（每个账户的首笔余额 = 基准 − 累计变动；合计口径与分账户口径的差额 = 没有基准余额的账户流过的钱；
汇总的收支总额 = 逐笔相加）。靠实际复现又找出 6 个问题，都已修掉并补了回归断言：

| 问题 | 后果 |
|---|---|
| 退款行只认「收/支 = 收入」 | 支付宝那种退款行写「不计收支」的账单里，**退了一笔账上却还多支出一次**，余额直接算错 |
| 退款净额只认「交易状态 = 已退款」 | 状态列写「交易成功」但有「成功退款」金额时，退款被忽略，支出算成全额 |
| 账户名叫 `constructor` / `__proto__` | 撞上原型链，**整条余额链条变成 NaN**，界面全是 NaN |
| 内部划转用原金额而不是净额 | 划转本身带退款时，账户余额按原额扣，账不对 |
| 基准余额填成负数 | 一声不吭（负余额警告只看"交易前余额"，基准本身是负数反而查不出来） |
| 删同名文件（`账单.csv` / `账单.csv#2`） | 用前缀判断归属，删前者会顺手清掉后者的排除记录 |

另外顺手修了两处小的：没填基准余额时 KPI「区间末笔交易」显示成半截的「 元」（现在是「待填写」）；
`localStorage` 里的数据损坏时不清掉，导致每次启动都读不出来、账本看着是空的。

退款这一块改完后的口径是：**退款要么标在原行上（按净额算），要么单列一行（按原额 + 退款入账冲回）**，
两种都在 `test/smoke-test.js` 的【14】节里有断言，且用真实的支付宝/微信表头跑过。

### 第五轮：换一套脑子独立审查（不是自己再读一遍）

这一轮请了一个**没参与过前四轮**的独立审查者，专门带着"会不会把账算错"这个问题去找茬。
所有结论我都自己复现过一遍才动手改。它判的是 **FAIL**，找出 1 个 P0 + 4 个 P1：

| 问题 | 后果 |
|---|---|
| 内部划转的"对向账户 == 目标账户"被折叠成单边入账 | **凭空造钱**：「零钱充值」那行的支付方式恰好是"零钱"时，对向账户被置空，于是记成"零钱 +500"，账户口径和合计口径同时被污染，界面零提示 |
| 收支方向识别失败的流水被静默丢弃 | 收/支 列名字对不上（比如写成"收入/支出"）→ 整份文件的钱全部归零，界面一声不吭，**体检还反报"全部匹配到划转规则"**，给人虚假的安全感 |
| 退款净额只认「交易状态 = 已退款」 | 状态列写「交易成功」但有「成功退款」金额时，退款被忽略 |
| 备份缺 `files` 段 → 退款口径退化成"按原样" | 手工改过的备份里，退款永远冲不回来，余额少一笔，还给出"退款行已单列"这种误导性提示 |
| 负数金额被当成支出 | `支出,-128.50` → 金额取负 → 变成 +128.50，**余额不降反升** |

另有 10 条 P2，包括「口径切换是空开关」（按账户/全部合计只改提示文案、数字一个不变）、
「排除关键词后不告诉你命中了几笔」、「基准余额写成字符串会被拼成 50100」等。

这一轮的修法：

- **自划转不再造钱**：对向账户与目标账户相同时按净额零处理，并在明细里标「对向账户与目标账户相同」
- **方向不明必须被看见**：新增体检第 7 项「收支方向识别」；警告区、质量面板、文件日志三处都会点名；
  微信账单里 `收/支` 写成 `/` 或留空（真实存在的中性流水写法）现在按"不计收支"处理，不再当成方向不明
- **退款口径能从数据本身推断**：不再依赖备份里的 `files` 段
- **负数金额取绝对值**并加标记
- **口径切换真的换列**：切到「全部合计」时明细表显示合计余额(前)/(后)，不再只是改一句提示文案
- **「亲属卡充值」规则方向修正**：微信官方口径是"钱从你的账户里扣，不是转给对方账户"，
  以前规则写成 `账户=微信·零钱, 方向=in`（等于"给亲属卡充钱自己零钱反而变多"），方向是反的

修完后又跑了 **500 组随机场景的模糊测试**（账户轨道 / 合计轨道 / 两口径差额 / 汇总守恒 / 无 NaN），
0 失败；自检从 202 涨到 **225 项断言**，全绿。

**还留着一条已知限制**：极少数「字段里有未转义逗号」的坏行，自动修复后商品名可能只保留后半截
（`买菜,日用品` 会变成 `日用品`）。金额、方向、时间这三列有硬锚点保护，**钱不会算错**，
只是显示的商品名不完整 —— 真实导出的账单里带逗号的字段是带引号的，基本不会触发这条路径。

## 七、常见问题

**Q：提示「未找到表头」**
A：导错了文件。要「账单明细」列表，不是概览。也可以确认文件没被 Excel 另存成 .xlsx（另存后表头会变）。

**Q：为什么某些行显示「—」**
A：该账户还没填基准余额，余额算不出来。填上就显示。

**Q：算出来的余额是负数**
A：多半是漏了更早的收入流水（比如工资在账单区间之前），或者基准余额填大了。
把基准日改成账单实际覆盖的最后一天，再核对一下有没有漏导某个月的账单。

**Q：支付宝的「花呗」消费怎么算**
A：花呗消费在账单里是「支出」，会从支付宝账户里扣；但花呗还款是「不计收支」。
如果你的支付宝账户余额里不包含花呗负债，可以在「③ 筛选 → 排除关键词」里排除掉。

**Q：能同时导入多个月的账单吗**
A：可以，全部拖进去就行。同名文件会自动加后缀，不会互相覆盖。

**Q：把同一个文件导了两次会怎样**
A：账本会比对**文件内容指纹**（不是文件名），发现是同一个文件时会弹窗问你，
默认建议跳过 —— 重复导入会让收入和支出直接翻一倍。想强行导入的话点「仍然导入」。

**Q：导入时看到「自动修复了 N 行列错位」是什么意思**
A：有些账单里的字段带了逗号但没加引号（多半是商品或商家名称），这一行从那列起会整体错开，
金额列就读成了「支出」这种非数字。账本会自动定位错位位置、把这一行的列重新对齐后照常解析，
不会丢这一笔。「⑤ 导入质量」里能看到每个文件修了多少行。

**Q：体检分数低要不要紧**
A：先看具体是哪一项。常见的是「账单月份连续性」报缺月份 —— 补导那一段账单，分数会自己涨上来。

**Q：能不能直接手记一笔**
A：可以，左侧「+ 手动记一笔」，现金支出、银行卡转账这类不在两个平台账单里的记录也能补进来，
同样参与余额反推。
